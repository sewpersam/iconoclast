## IoU gate

Reference renderer: `inkscape` 1.4.4 at `/usr/bin/inkscape`, run as 4
`--shell` processes. rsvg-convert and resvg are not installed and were not
used.

Method:

- Each SVG is exported by inkscape at 384 px, with the page area and a
  transparent background. The PNGs are cached in
  `render/build/verify/inkscape-384/` and reused while newer than the SVG.
- Each bundled icon goes through `AwtRasterizer`, behind the `:render`
  `IconRasterizer` interface. It uses java.awt with the recorded stroke
  width, caps, joins, miter limit and fill rule, at 384 px.
- Both 384 px alpha masks are box-filtered to **96 px**, then compared.
- Score: soft IoU, the sum of per-pixel minimum alpha over the sum of
  per-pixel maximum alpha. Pass at 0.98 or more.

| Measure | Value |
|---|---|
| Icons | 15,322 |
| Soft IoU below 0.98 | **5** |
| Pass rate | **0.99967** (gate 0.999) |
| Min, 0.1st pct, 1st pct | 0.9018, 0.9898, 0.9919 |
| Median, mean | 0.9961, 0.9959 |
| Binary IoU at alpha 128 below 0.98, not gated | 178, median 0.9979 |
| Inkscape references, cold | 20.6 s for 15,322 |
| Rasterize and compare | 30.1 s, 4 workers |

The 5 failures fall into two classes. Neither is a converter defect.

| Icon | Soft IoU | Cause |
|---|---|---|
| cino | 0.9018 | `opacity:.9` on every shape. Inkscape paints at 90% alpha |
| fairtiq | 0.9732 | `opacity:.97` on most shapes |
| suzuki | 0.9358 | Cusp cubic. Inkscape draws a hairline |
| royal_road | 0.9386 | Cusp cubic. Inkscape draws a hairline |
| nekome | 0.9767 | Cusp cubic. Inkscape drops a wedge of two whiskers |

- Opacity: the converter drops paint opacity on purpose, because the
  restyle sets its own paint. The geometry matches. Only the reference's
  alpha is lower.
- Cusp cubics: the source holds a cubic with a control point on, or almost
  on, an end point. Examples are `c0,0-23.17-16.2393-23.1695-16.2396` in
  suzuki, `0,0-15.8266,0-15.8149,0` in royal_road and
  `c0,.0207-4.8629-1.5138-4.8629-1.5138` in nekome. The suzuki and
  royal_road curves run about 26 and 16 units, and SVG strokes them at
  full width. Inkscape draws a hairline there, and for nekome a whisker
  missing a wedge. All three are visible in the 384 px references. The
  bundle keeps each cubic as written, so the icon draws as designed.

## Why the comparison supersamples

The spec says inkscape renders "at the same size". The first runs did that
at 96 px, and three effects outweighed any converter error:

1. **Coverage ties at alpha 128.** A 2 px stroke centred on a half pixel
   leaves edge pixels at exactly 50%. Cairo gives 119 and 136, and Java2D
   gives 127 and 127. A binary mask flips them, so 2,435 icons failed
   binary IoU.
2. **Java2D row quantisation.** Marlin samples 8 sub-rows per pixel by
   default. `sun.java2d.renderer.subPixel_log2_Y=8` fixes it. A probe
   line at y = 19.3 px then gives 178 and 76, the exact values.
3. **Reference error on curves.** For a stroked circle in babydots, against
   an analytic 16 by 16 supersampled ring, soft IoU is 0.961 for
   inkscape at 96 px. Our 4x supersampled raster scores 0.991. At 96 px,
   cairo's curve flattening is the larger error.

Progress, every row from a run of `verifyIconConversion`:

| Configuration | Below 0.98 |
|---|---|
| Binary IoU, both at 96 px | 2,435 |
| Soft IoU, both at 96 px | 876 |
| Plus the Marlin sub-row fix | 268 |
| Plus both sides at 384 px, box-filtered to 96 | 9 |
| Plus curves flattened to 0.002 units before Java2D strokes them | 5 |

Supersampling both sides gives both masks near-exact coverage. The score
then measures geometry, not two antialiasers. The output is still compared
at 96 px. The flattening step affects only the JVM test rasterizer. Java2D
offsets tight cubics badly, and wavelet and panels improved with it.

## Gate validated against broken converters

Each mutation was a temporary edit, run, then reverted with `git checkout`.
No mutation switch is left in the code. Each row comes from
`./gradlew verifyIconConversion` and `./gradlew :build-logic:test` with the
mutation in place.

| Mutation | verifyIconConversion | Unit tests |
|---|---|---|
| None, the control | 5 below 0.98, pass rate 0.99967, PASS | 31 pass |
| (a) Sweep flag inverted at `PathData.kt:163`, as `largeArc == !sweep` | Build fails before the gate: the encoder rejects coordinate 131.17 as out of range | `quarterArcFlagsPickCentreAndDirection` fails |
| (a) again, with the coordinate range widened, `COORD_SCALE` 256 to 64, so the gate sees it | **2,776** below 0.98, pass rate 0.81882, **FAIL**. Worst: myzong 0.0115 | n/a |
| Control for that widening, `COORD_SCALE` 64 alone | 5 below 0.98, pass rate 0.99967, PASS | n/a |
| (b) Transform baking skipped, `val transform = parentTransform` | **314** below 0.98, pass rate 0.97951, **FAIL** | `transformsAreBaked` fails |
| (c) Radius scaling dropped, `if (lambda > 1)` made `if (false)` | 5 below 0.98, pass rate 0.99967, **PASS** | `relativeArcWithCompactFlagsAndRadiusScaling` fails |

The gate rejects (a) and (b). **It does not reject (c).** The data explains
why. A temporary probe counted 21,611 arcs at the pin. Only 291 need radius
scaling, and their largest lambda is 1.0307: 207 are below 1.0001, 73 below
1.01 and 11 below 1.1. These are radii rounded just under half the chord.
Dropping the scaling moves those arcs by at most about 1.5% of their
radius, below what IoU at 96 px can see. The bundle changed by 286 bytes.
The unit test rejects (c). So the gate checks visible geometry on this
data, and the unit tests check the exact arc maths.

## Rasterizer deviation, open for M2

The gate does not run the shipping `:render` code path. `AwtRasterizer`
lives in the JVM-only `verify` source set and never ships. It stands in
because Task 3 picks the Android-side rasterizer.

Task 3 (M2) must re-run `./gradlew verifyIconConversion` with its
production `IconRasterizer` and the gate must still pass. The swap is one
line: `rasterizerUnderTest()` in
`render/src/verify/kotlin/dev/icondesigner/render/verify/VerifyConversion.kt`.
The `IconRasterizer` KDoc records the same requirement.
