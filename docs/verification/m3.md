## Launcher findings

- **N1. No `res/xml/appfilter.xml` stub.** Spec 3.4 asks for a minimal stub. With an
  empty stub, Neo showed stock icons after selecting the pack and after Force stop.
  Kvaesitso's dex carries `Searched locations: res/xml/appfilter.xml, res/raw/appfilter.xml,
  assets/appfilter.xml`, so a launcher that finds the stub never reads the assets copy.
  The template ships no res/xml appfilter. Every launcher then read `assets/appfilter.xml`,
  as the spike proved. Commit "Drop the empty res/xml appfilter stub".
- **N2. Neo refresh recipe.** Spec 1.3 says a launcher restart always fixed staleness.
  On these AVDs Neo's own Restart entry (Home settings, top-right menu, Restart) refreshed
  once and failed once; Force stop failed once; switching to System icons and back without
  a restart failed (shots `icondesign36_neo_7`, `_8`). Restart followed by the switch worked
  both times it was run (`icondesign36_neo_13c`, `icondesign_neo_8c`). That is the shipped
  guidance.
- **N3. Neo, Phone on first selection.** On both AVDs the dialer kept its stock icon right
  after the first selection while every other app was themed. Its appfilter entry is correct
  (`com.android.dialer/com.android.dialer.main.impl.MainActivity` to `slot_0012` on AOSP).
  One refresh themed it. Not fixed; a Neo icon-cache race is the likely cause, unproven.
- **N4. Neo lists a new pack only after Restart** on the API 35 AVD
  (`icondesign_neo_2-picker-pack-missing`, `_4-picker-after-restart`). On API 36 after
  clearing Neo's data it was listed at once. The first-time guidance covers both.
- **N5. Lawnchair's "Restart Lawnchair"** is the `debug_restart_launcher` string, only in its
  hidden debug menu. Lawnchair uses Force stop from App info, which the designer deep links to.
- **N6. `assets/drawable.xml` works in both pickers.** Neo and Lawnchair per-app icon pickers
  list the used slots. A probe pack whose drawable.xml lists 3 slots made both pickers show
  exactly 3, so they read the file and do not fall back to the appfilter. The probe was the
  installed pack with only `assets/drawable.xml` replaced, re-signed with the designer's key
  read through `run-as`.
- **N7. Updates without the prompt.** In the first runs every update showed "Do you want to
  update this app?" despite `USER_ACTION_NOT_REQUIRED`. Review re-check on icondesign36 with
  Lawnchair: declaring `UPDATE_PACKAGES_WITHOUT_USER_ACTION` alone (granted) still prompted
  (`icondesign36_lawnchair_10-update-prompt-permission-only`). From API 34 update ownership is
  enforced, so the designer now also declares `ENFORCE_UPDATE_OWNERSHIP` and calls
  `setRequestUpdateOwnership(true)`. Ownership is set only by a fresh install: after uninstalling
  the pack, the first install still prompted (`_11-fresh-install-prompt`), `dumpsys` showed
  `updateOwnerPackageName=dev.icondesigner.app`, and the next update installed with no prompt,
  `install: Success in 102 ms` (`_12-update-without-prompt`). A pack installed by an older build
  has no owner and keeps prompting until it is reinstalled. Not re-checked on the API 35 AVD.
- **N8. No launcher reload intent** was found or shipped. Neo's dex contains
  `com.farmerbb.taskbar.REFRESH_DESKTOP_ICONS`, but its manifest has no receiver for it and a
  runtime receiver was not checked;
  not tested further.
- **Intent filters.** The six actions of spec 3.4 are the only icon pack actions found as
  strings in the three launchers' dex: Neo has all six except `org.adw.ActivityStarter.THEMES`,
  Lawnchair has `com.novalauncher.THEME`, `com.anddoes.launcher.THEME`,
  `com.dlto.atom.launcher.THEME`, Kvaesitso has `org.adw.launcher.THEMES`,
  `org.adw.ActivityStarter.THEMES`, `com.novalauncher.THEME`. `app.lawnchair.icons.THEMED_ICON`
  appears only in Kvaesitso and is not added: it marks monochrome themed-icon sources, which
  this pack is not. Not tested.
- **Pack activity.** `am start -n dev.icondesigner.app.pack/dev.icondesigner.templatepack.OpenDesigner`
  resumed `dev.icondesigner.app/.MainActivity` (`icondesign36_pack_activity-opens-designer`).

## Phone budgets, spec 3.3

`PhoneBudgetTest` in `:app` androidTest, run with `am instrument -e class
dev.icondesigner.app.PhoneBudgetTest#<method>`, one method per process so the first run is a
cold process. Each run uses a new `IconRenderer`, so the mask cache is always cold. Debug APK,
4 vCPUs per AVD, emulator 37.3.3, headless, `-gpu host`.

- Preview: the 24 golden sample icons at 128 px, plain theme, `render` only.
- Apply: a synthetic 300-drawable plan spread evenly over the 15,322 icons, invert fill,
  432 px, through `PackBuilder.build`: 301 renders and PNG encodes including the pack icon,
  on `Dispatchers.Default.limitedParallelism(4)`, then the template rewrite. 4,446,012 bytes.

| AVD | Preview, ms per run, first cold | Apply, ms per run, first cold |
|---|---|---|
| icondesign36, API 36 | 164, 55, 51, 47 | 7,780, 7,214, 7,225, 7,210 |
| icondesign, API 35 | 194, 60, 54, 48 | 7,996, 7,392, 7,378, 7,355 |

- Apply: **PASS**, 7.2 to 8.0 s against 20 s, cold process included.
- Preview after the first: **PASS**, 47 to 60 ms against 150 ms.
- Preview, first render in a new process: **FAIL**, 164 and 194 ms against 150 ms. The
  extra 110 to 140 ms is class loading and JIT warm-up of the render path. Not tuned in this
  pass. The test gates the runs after the first and logs the first.

Caveats: the emulator runs x86_64 on a 24-core desktop host, not a Pixel 6a-class phone.
A debuggable APK runs without AOT compilation, which slows the cold run.

## Template

Built by `:template-pack:buildTemplatePack` with aapt2 and d8 from build-tools 36.0.0:
316,373 bytes, 1024 slots of a 70-byte transparent PNG stored, `pack_icon.png`, stored
`resources.arsc`, `assets/appfilter.xml`, `assets/drawable.xml`, the CC BY-SA 4.0 legal code
(`licenses/CC-BY-SA-4.0.txt`, from creativecommons.org) and `NOTICE.txt`, and one 1.9 KB dex
with `OpenDesigner`. The build fails if the dex references the Kotlin runtime.

Reproducible across builders (final review fix). The build JDK's zlib never touches the
template: Fedora's is zlib-ng, Debian's is stock zlib, and they deflate differently.

- Raw-copied from aapt2's `linked.apk`, compressed bytes unchanged: all 1,031 aapt2 entries.
  Deflated by aapt2: `AndroidManifest.xml`, `assets/LICENSE-CC-BY-SA-4.0.txt`,
  `assets/NOTICE.txt`. Stored by aapt2: the 1,025 PNGs, `resources.arsc`,
  `assets/appfilter.xml`, `assets/drawable.xml`.
- Stored, added by the task: `classes.dex`, 1,952 bytes.
- The placeholder PNG is a fixed 70-byte array, not ImageIO output.
- Every entry gets DOS time 1981-01-01 00:00, no data descriptors, no extra fields.

Before the fix the JDK re-deflated the manifest to 1,029 bytes and the licence to 6,198,
against aapt2's 1,023 and 6,185. Tests: `TemplateZipTest` in `:build-logic`, raw bytes kept
and the dex stored; `TemplateReproducibleTest` in `:template-pack`, two independent builds
(`buildTemplatePack`, `buildTemplatePackAgain`) are byte identical, SHA-256
`d4694a783b8f2fe2450c2953bc147ea5aedf706f404309f1e60b5af4c5bca895`, and each aapt2 entry
keeps its method, CRC and compressed size. The template still depends on the aapt2 and d8
binaries of build-tools 36.0.0 being the same on both builders.

Slot count stays 1024: a heavily used phone has 300 to 500 launchable apps, and the empty
slots cost about 300 bytes each in the template. Above 1024 the designer shows
"N apps have icons, but a pack holds at most 1024".
